---
name: Mass-unit DB target validation
description: Verify a database dump is from the same development database the app actually uses before profiling mass-unit migration.
---

Before profiling or rehearsing a mass-unit migration, distinguish the runtime database from any export/source database. In Replit the same `DATABASE_URL` name can point to separate development and production databases; the shell value typically targets development. This app's runtime and confirmed dev data source use `DATABASE_URL`; the production target must be matched to the Published app.

The production host `neon.tech` does not by itself prove that the database is external; Replit-managed PostgreSQL can be Neon-backed. In this project, the user accesses Production through Replit Database and Publish exposes a managed schema diff. Treat the target as Replit-managed unless Replit's settings confirm otherwise. `explainSchemaDiff()` compares the schema Replit Publish would apply; verify that it is the same target as the Published app before relying on it. The production dump had no exact raw `75` kg-rate row, although that approved anomaly existed in development.

- Before publishing to a Replit-managed database, inspect `explainSchemaDiff()`. Keep new mass columns nullable through the expand/backfill release and preserve kg fallbacks until backfill. Tighten to NOT NULL only in a later source-schema release after production data checks, so Publish cannot revert out-of-band constraints. Preserve unrelated production-only schema objects rather than dropping them in the unit cutover; compare partial unique indexes and `ON DELETE` behavior too. Replit Publish owns structural DDL, and the agent must not create or run production migration scripts or deploy hooks. Any production data migration is a separate, explicitly owner-initiated action through a supported Replit workflow.

**Why:** Schema size, row counts, and a provider hostname do not establish that two connections refer to the same database. Some shared rows had conflicting mass/price values; timestamps favored the runtime DB where available, but several conflicts had no usable timestamp. Replit-managed production can use Neon infrastructure, so host-only classification can wrongly exclude the actual app database. Publish diffs do not execute the historical unit-conversion backfill; adding new NOT NULL columns directly to populated production tables can produce truncation operations.

**How to apply:** Confirm the runtime target from Replit Database/Publishing settings and compare it with the dump and schema diff without printing credentials. Restore backups only into disposable local PostgreSQL. Do not use `updated_at` as the sole authority when it is absent; inspect audit/business history or ask the user to choose a winner. Treat `executeSql(environment="production")` as read-only access to Replit-managed production; verify whether it is the Published app target before profiling or writing. For a confirmed external database, follow its separately approved migration workflow. A guarded one-off repair should accept zero or one exact approved match, and abort on duplicates or other shapes. For historical mass backfill, convert saved kg values to tonnes; do not replace them with `liters × density`. Use deal density for per-liter price equivalents, preserve stored sums, and route mismatches for review. After the configured post-merge sync, re-run the publish diff; keep schema-only compatibility declarations for unrelated empty production objects until their separate cleanup is approved.
