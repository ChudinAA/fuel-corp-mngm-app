Before profiling or rehearsing a mass-unit migration, distinguish the runtime database from any export/source database. In Replit the same `DATABASE_URL` name points to separate development and production databases; the shell value typically targets development. This app's runtime and confirmed dev data source use `DATABASE_URL`; production remains a separate database.

The user verified the production connection host as `neon.tech`, identifying the app's production target as external Neon. The Replit-managed production database exposed by `executeSql(environment="production")` is not the app's Neon production database. A production dump exported through Replit's Production connection details had no exact raw `75` kg-rate row, although that approved anomaly existed in development.

**Why:** Schema size and row counts do not prove two databases contain equivalent records. Some shared rows had conflicting mass/price values; timestamps favored the runtime DB where available, but several conflicts had no usable timestamp. A production host check showed `neon.tech`, so Replit-managed production SQL would profile a different database. Target-specific repairs also may have no matching rows outside the environment where an anomaly was observed.

**How to apply:** Confirm the runtime URL from code and the target from the user's decision without printing credentials. Restore alternate sources into disposable local PostgreSQL and compare overlapping records before retiring them. Do not use `updated_at` as the sole authority when it is absent; inspect audit/business history or ask the user to choose a winner. Treat production as separate from the shell's dev `DATABASE_URL`. Replit's `executeSql(environment="production")` only queries Replit-managed PostgreSQL; for this external Neon production, use the Production connection details in Replit and export through Shell with `pg_dump`, without printing the URL or replacing dev `DATABASE_URL`. Verify the dump source before profiling. A guarded one-off repair should accept zero or one exact approved match, and abort on duplicates or other shapes. For historical mass backfill, convert saved kg values to tonnes; do not replace them with `liters × density`. Use deal density for per-liter price equivalents, preserve stored sums, and route mismatches for review.
