---
name: Mass units and precision
description: Product decisions for converting mass, prices, and litre-based rates to tonnes.
---

- Masses are represented in tonnes and shown with up to five decimal places, trimming trailing zeroes. This preserves legacy precision of 0.01 kg as 0.00001 t without noisy fixed zeros.
- Prices per tonne are shown with two decimal places. Keep calculation/storage precision sufficient to preserve existing transaction totals; do not round unit rates early.
- When an unchanged legacy rate is shown rounded as ₽/т, preserve the exact stored ₽/кг value on save; display rounding must not rewrite stored precision.
- Convert rates per kilogram to rates per tonne by multiplying by 1,000.
- Keep master per-litre tariffs in ₽/л as reusable source quotes; convert to ₽/т at deal level using that deal's density. Preserve the transaction amount as litres × the source per-litre rate.
- For historical deal rates, prefer saved amount ÷ saved tonnes when the amount exists, preserving the current displayed effective rate; only use deal density to convert a per-litre rate when no saved amount exists.
- Historical БДР `salesVolume` values must be recomputed by month from non-deleted OPT and refueling quantities; only this field is replaced, while `salesRevenue` and other budget fields remain unchanged.
- Management-report government-contract summaries must keep financial amounts in ₽ separate from planned, actual, and remaining mass in tonnes.
- Monetary totals and the signs/directions of stock movements must not change during unit conversion.
- Runtime APIs and UI use tonnes and ₽/т; do not add kg-only inputs, response aliases, fallback reads, or mirror writes back.
- Stop using kg mirrors where the tonne field is populated and verified. Keep old physical columns inert until their separate schema cleanup.
- If a table still lacks a tonne-authoritative field or has unbackfilled tonne values, add/backfill that source before removing its kg conversion; do not hide the gap with a fallback.
- Only normalize a raw numeric `prices.price_values` scalar as a rate when its unit/meaning has been explicitly reviewed; the approved dev anomaly was exactly one `75` value in a `kg` row, converted to a standard `75000` per-tonne rate.
- Dashboard warehouse balances show only the current balance in tonnes. Do not treat `storageCost` (₽/т) or `limitVolume` (monthly throughput) as physical capacity; disable capacity alerts until a real capacity field exists.

**Runtime cleanup rule:** No observation window is required. The user explicitly authorized removing runtime kg compatibility immediately, while keeping physical database-column removal as a separate schema cutover.

**Why:** The user said the upcoming 1C integration will use tonnes and that kg API branches, mirrors, fallbacks, and adapters would add confusion and complexity. Current code inspection also found some storage paths that are still genuinely kg-backed, so those need tonne data fields and backfill before their adapters can be removed safely.

**How to apply:** Make runtime API contracts tonne-only and remove compatibility module-by-module after checking the authoritative tonne data exists. Do not wait for an observation period. Do not remove physical columns or rewrite historical migration files in the runtime cleanup; handle those in a separate reviewed schema cutover.

**Why:** The user requires mass precision to remain at five decimal places after conversion, while prices display two decimals, and explicitly chose to preserve existing totals for historical per-litre deals. Per-litre rates cannot be converted to a universal per-tonne value without the deal's density. Where a saved total exists, the app already exposes total divided by saved mass as the effective rate; retaining that value avoids changing the established UI while preserving the total. Use density only when a historical per-litre rate has no saved total. Rounded rate displays must not cause no-op edits to overwrite higher-precision saved rates. Price rates and contract masses need separate unit markers because a price may be quoted per litre while its limit and used quantity are masses. Historical deal mass can differ from liters multiplied by density; every historical transaction mass must use its saved mass, while density is used only to convert a per-liter rate with no saved total or process new liter input. The dashboard's former capacity display compared a mass balance with a per-tonne price, so the user chose to show only actual balances until physical capacity is modeled. One БДР auto-fill path has stored revenue in the mass field, so the user chose to rebuild that field from transaction quantities. The user also chose to see both money and tonnes as separate government-contract metrics, and asked that each migration stage record completed work, remaining work, and new findings to preserve context. The raw scalar was interpreted as a rate only after the user approved this specific known value; that approval does not authorize converting other malformed rows.

**How to apply:** Keep calculations, UI, API input, and API output in tonnes/₽ per tonne. For prices, update `price_unit` with stored rate values and `volume_unit` with contract mass values, and update `sold_volume` atomically if its unit changes. Remove kg mirrors, API aliases, and fallback reads where the tonne source is complete; if it is not, add and backfill tonne storage first. Do not drop physical columns or rewrite historical migration SQL in this runtime step. For every historical operation, use its saved mass; never reconstruct it from liters × density. For a historical rate, use saved amount ÷ saved tonnes when an amount exists; otherwise convert a per-litre rate with deal density. Use density for new liter input and preserve stored historical totals. Recalculate active БДР monthly sales volumes from non-deleted OPT/refueling quantities, changing no other budget fields. In contract summaries, report contract amounts as money and planned/actual/remaining quantities as tonnes; never subtract unlike units. Follow these rules in forms, stock and cost calculations, reports, audit displays, and exports. Reconcile totals and balances before production cutover. On dashboards, display current balances only unless a dedicated physical-capacity field is available. For similar raw scalar price records, verify the source unit and record shape before broadening a reviewed one-off repair. After every completed migration stage, update `docs/MASS_UNIT_MIGRATION_STATUS.md` with what is complete, what remains, and any new findings.
