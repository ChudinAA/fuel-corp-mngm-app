---
name: Mass units and precision
description: Product decisions for converting mass, prices, and litre-based rates to tonnes.
---

- Masses are represented in tonnes and shown with five decimal places. This preserves the legacy precision of 0.01 kg as 0.00001 t.
- Prices per tonne are shown with two decimal places. Keep calculation/storage precision sufficient to preserve existing transaction totals; do not round unit rates early.
- When an unchanged legacy rate is shown rounded as ₽/т, preserve the exact stored ₽/кг value on save; display rounding must not rewrite stored precision.
- Convert rates per kilogram to rates per tonne by multiplying by 1,000.
- Convert a per-litre rate to an equivalent per-tonne rate using the density recorded for that specific deal. Preserve the transaction amount as litres × the source per-litre rate.
- For historical deal rates, prefer saved amount ÷ saved tonnes when the amount exists, preserving the current displayed effective rate; only use deal density to convert a per-litre rate when no saved amount exists.
- Historical БДР `salesVolume` values must be recomputed by month from non-deleted OPT and refueling quantities; only this field is replaced, while `salesRevenue` and other budget fields remain unchanged.
- Management-report government-contract summaries must keep financial amounts in ₽ separate from planned, actual, and remaining mass in tonnes.
- Monetary totals and the signs/directions of stock movements must not change during unit conversion.
- During staged rollout, keep untagged legacy mass fields in kg. For prices, `price_unit` labels the stored rate array while `volume_unit` independently labels contract mass and usage; update each unit marker atomically with its values.
- For logistics capacities, warehouse monthly limits, warehouse/equipment balances and ledger masses, and transportation/ordinary/equipment movement masses and rates, treat tonne columns as authoritative and synchronize legacy kg mirrors until old readers are removed. Every historical transaction mass comes from saved kg, never liters × density.
- When an edit submits both tonne and legacy kg values, compare each with the saved row: if only kg changed, preserve that legacy edit and recompute tonnes; otherwise tonnes lead. Continue accepting kg-only legacy writes during staged rollout.
- Dashboard warehouse balances show only the current balance in tonnes. Do not treat `storageCost` (₽/т) or `limitVolume` (monthly throughput) as physical capacity; disable capacity alerts until a real capacity field exists.

**Why:** The user requires mass precision to remain at five decimal places after conversion, while prices display two decimals, and explicitly chose to preserve existing totals for historical per-litre deals. Per-litre rates cannot be converted to a universal per-tonne value without the deal's density. Where a saved total exists, the app already exposes total divided by saved mass as the effective rate; retaining that value avoids changing the established UI while preserving the total. Use density only when a historical per-litre rate has no saved total. Rounded rate displays must not cause no-op edits to overwrite higher-precision legacy rates. Price rates and contract masses need separate unit markers because a price may be quoted per litre while its limit and used quantity are masses. Existing consumers may rely on legacy kg properties for logistics capacity, warehouse limits, and warehouse/equipment stock and ledger fields during staged rollout, so new tonne fields are authoritative while synchronized mirrors preserve compatibility. Older clients or restored records may submit a stale tonne value alongside a changed kg value; blindly preferring tonnes can silently discard the edit. Historical deal mass can differ from liters multiplied by density; every historical transaction mass must use saved kg, while density is used only to convert a per-liter rate with no saved total or process new liter input. The dashboard's former capacity display compared a mass balance with a per-tonne price, so the user chose to show only actual balances until physical capacity is modeled. One БДР auto-fill path has stored revenue in the mass field, so the user chose to rebuild that field from transaction quantities. The user also chose to see both money and tonnes as separate government-contract metrics, and asked that each migration stage record completed work, remaining work, and new findings to preserve context.

**How to apply:** Keep calculations and UI in tonnes/₽ per tonne. Do not write tonnes into untagged legacy fields; for prices, update `price_unit` with the stored rate values and `volume_unit` with contract mass values, and convert `sold_volume` in the same update when its unit changes. For logistics capacity, warehouse limits, warehouse/equipment balances and ledger masses, transportation and other movement mass/rates, write tonne values and kg mirrors atomically; reads prefer tonnes and fall back to saved kg only for legacy rows. When both mass fields arrive on an edit, compare them with the saved row and use kg only if that is the field that changed by itself; otherwise use tonnes and synchronize the mirror. If only one unit is present, derive its mirror. Remove compatibility adapters only during coordinated cutover. For every historical operation, backfill/read mass from saved kg; never reconstruct it from liters × density. For a historical rate, use saved amount ÷ saved tonnes when an amount exists; otherwise convert a per-litre rate with deal density. Use density for new liter input and preserve stored historical totals. Recalculate active БДР monthly sales volumes from non-deleted OPT/refueling quantities, changing no other budget fields. In contract summaries, report contract amounts as money and planned/actual/remaining quantities as tonnes; never subtract unlike units. Follow these rules in database migrations, forms, stock and cost calculations, reports, audit displays, and exports. Reconcile totals and balances before production cutover. On dashboards, display current balances only unless a dedicated physical-capacity field is available. After every completed migration stage, update `docs/MASS_UNIT_MIGRATION_STATUS.md` with what is complete, what remains, and any new findings.
