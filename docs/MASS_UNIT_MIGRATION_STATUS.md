# Масса и цены: переход на тонны

## Зафиксированные требования

- Массы, остатки, лимиты и транспортные ёмкости переводятся в тонны и отображаются с 5 знаками после запятой.
- Удельные цены за тонну отображаются с 2 знаками после запятой. Внутреннюю точность нельзя преждевременно округлять, если это меняет суммы.
- Цена за кг переводится в цену за тонну умножением на 1 000.
- Цена за литр пересчитывается в эквивалент цены за тонну по плотности конкретной сделки. Сумма сделки остаётся равной исходной цене за литр, умноженной на литры.
- Денежные итоги, знаки складских движений и связи движений со сделками должны сохраниться.
- Миграции данных не запускаются до согласованного обновления кода и проверки на резервной/копийной базе.

## Карта хранимых данных

### Масса, остатки, ёмкости и лимиты

- Сделки и движения: `opt.quantity_kg`, `aircraft_refueling.quantity_kg`, `refueling_abroad.quantity_kg`, `movement.quantity_kg`, `equipment_movement.quantity_kg`, `transportation.quantity_kg`.
- Склады: `warehouses.current_balance`, `pvkj_balance`, `limit_volume`; `warehouse_transactions.quantity`, `balance_before`, `balance_after`.
- Топливозаправочная техника: `equipments.current_balance`, `pvkj_balance`; `equipment_transactions.quantity`, `balance_before`, `balance_after`.
- Карты хранения: `storage_cards.current_balance` и `storage_card_transactions.quantity`, `balance_before`, `balance_after` — денежные остатки/движения в USD, а не масса; их нельзя умножать или делить на 1 000 как массу.
- Массовый эквивалент баланса карты можно вычислить только по известной цене и единице цены. Для цены за литр нужна плотность конкретной сделки; без неё тоннаж не показывать.
- Планирование: объёмы и балансы в `plan_entries`, `free_volume_allocations`, `supplier_allocated_volumes`, `planning_top_level_volumes`.
- Логистические справочники: вместимость автомобилей и прицепов `capacity_kg`.
- Договорные объёмы и уже проданные объёмы цен: `prices.volume`, `prices.sold_volume`.
- Отдельно проверить агрегаты/JSON и сохранённые снимки аудита; это не ограничивается колонками с суффиксом `_kg`.

### Удельные цены и исключения

- Цены/себестоимость за кг встречаются в сделках, движениях, складских и equipment-остатках, ценах поставщиков и тарифах доставки.
- Значения массива `prices.price_values` сериализованы в `text[]`; для элементов с `price_unit = kg` нужно преобразовать цену и перейти к единице за тонну.
- Записи `price_unit = liter` нельзя превратить в постоянную цену за тонну без плотности. Исходную цену сохранять для расчёта суммы; эквивалент ₽/т вычислять по плотности конкретной сделки.
- Уже тонные значения биржевых весов и железнодорожных тарифов (`weight_ton`, `actual_weight_ton`, `price_per_ton`) повторно не конвертировать.
- `warehouses.storage_cost` и услуги типа `royalty_per_ton` уже используются как ставки за тонну; не умножать их на 1 000.
- Для `service_value`, `other_service_quantity`, фиксированных услуг и процентных ставок единица определяется типом услуги; не конвертировать эти поля массовым правилом.

## Отчёт по этапу 1

- Сверены Drizzle-сущности и расчётные места, где единицы не следуют из имени поля.
- Зафиксированы данные, которые преобразуются, ставки, которые масштабируются, уже тонные поля, и поля, которые нельзя конвертировать универсально.
- Найдено около 120 клиентских/серверных файлов со ссылками на массу и удельные цены.
- Выбрана стратегия: код и схему переключать согласованно; миграцию не запускать при старом коде.
- Проверка: общие функции конверсии и 5 unit-тестов проходят; `tsc --noEmit` проходит.

Следующий этап: переводить серверные расчёты и API группами связанных потоков, сохраняя исходные денежные суммы и знаки складских операций. Только после завершения серверной и клиентской части готовить cutover исторических данных.

### Этап 2 — текущий прогресс

- В потоке «биржевая сделка → складское движение» расчёт количества и себестоимости теперь остаётся в т и ₽/т; перевод в кг и ₽/кг выполняется только на границе старых таблиц.
- Этот участок временно сохраняет legacy-контракт движения и склада в кг, поэтому поведение текущего UI и БД не меняется.
- Проверка: 5 тестов конверсии проходят, `npm run check` и `git diff --check` проходят.
- Это не завершает переход серверной части: основные сущности, API и складские цепочки всё ещё работают в кг. Пока не готова общая конверсия, не применять миграцию данных.

#### Подэтап 2.4 — карточки хранения и производные массовые показатели

- Статус: завершён для карточек хранения; денежные поля карточек классифицированы и сохранены без масштабирования.
- Баланс карточки и суммы её транзакций остаются в USD. Для сводного эквивалента цены за кг переводятся в цену за тонну; цена за литр показывается за литр, а тоннаж без плотности сделки не вычисляется.
- История связанных с карточкой сделок заправки показывает массу в тоннах: если есть литры и плотность, используется их произведение (оно надёжнее потенциально некорректного legacy-поля `quantity_kg`); иначе используется сохранённая масса.
- Для несвязанных исторических транзакций единица сохранённой цены не всегда известна, поэтому массовый эквивалент и цена за тонну отображаются как недоступные вместо предположения, что цена была за кг.
- Проверено: `npm run check`; 11 unit-тестов конверсии/карточек; 33/33 теста `npm run test:critical-flows`; `git diff --check`.
- Ограничение: неоднозначные старые транзакции без связи со сделкой не получают вычисленный тоннаж; преобразование схемы и данных БД не выполнялось.

#### Подэтап 2.5 — зарубежные заправки, тонный ввод и пересчёт цен

- Статус: завершён на совместимой границе текущей схемы.
- Новые сделки по умолчанию вводятся в тоннах с точностью 5 знаков. На legacy API границе масса переводится в физические кг; для литровой сделки отдельно сохраняются литры и масса, вычисленная по плотности сделки.
- Цена за кг переводится в ₽/т или USD/т умножением на 1 000. Цена за литр переводится в цену за тонну по плотности конкретной сделки; денежные суммы остаются равны исходной цене за единицу × исходное количество.
- Таблица сделок показывает массу в тоннах и удельные цены за тонну с 2 знаками; для литровых сделок сохраняется видимый объём в литрах. Комиссия `royalty_per_ton` рассчитывается напрямую от тонн.
- Лимит договора использует литры для цены с `price_unit = liter` и кг для цены с `price_unit = kg`; интерфейс показывает соответственно литры или тонны. Для незавершённой литровой сделки сервер требует положительную плотность.
- Проверено: `npm run check`; 16 unit-тестов конверсии/карточек/зарубежных заправок; `npm run test:critical-flows` — 33/33; `git diff --check`.
- Остаётся: остальные сущности/API и формы приложения, отчёты/экспорт, а затем сквозная миграция исторических данных и согласованный cutover схемы. База данных и исторические значения в этом подэтапе не изменялись.

#### Подэтап 2.6 — внутренние заправки, тонный ввод и лимиты договоров

- Цены и ставки в форме, дополнительных продуктах и таблице показываются за тонну с 2 знаками. Для литровых сделок эквивалент зависит от плотности; денежные суммы сохраняют исходную цену × исходное количество.
- Комиссия за кг считается в пересчёте на тонны; уже тонная `royalty_per_ton` остаётся без дополнительного масштаба. Остатки склада и ТЗК показываются в тоннах, но передаются старым складским API как кг.
- Для лимита цены за литр используется объём в литрах, для цены за кг — масса в кг. Для незавершённой сделки в литрах сервер и форма требуют положительную плотность.
- Проверено: `npm run check`; 6 новых unit-тестов; 16 тестов конверсии/заправок; `npm run test:refueling-order` — 2/2; `npm run test:critical-flows` — 33/33; `git diff --check`.

## Текущее ограничение

Документ и общие функции конверсии не переключают работающие модули. Пока сервер и интерфейс используют действующий контракт в кг, не менять числовые значения массы в БД и не запускать миграцию: это создало бы смешение единиц. Денежные балансы карточек хранения не являются массовыми значениями и не участвуют в такой конверсии.
