# Интеграция 1С: справочники

## Документация API

- Swagger UI: `/api/integrations/1c/docs`
- OpenAPI JSON: `/api/integrations/1c/openapi.json`
- API v1: `/api/integrations/1c/v1`

Swagger/OpenAPI доступны без пользовательской сессии, чтобы внешние разработчики могли открыть документацию. Для всех методов API v1 нужен отдельный ключ интеграции:

```http
Authorization: Bearer <key>
Content-Type: application/json
```

Ключ выпускает администратор на странице «Интеграция с 1С». Он показывается только при создании или перевыпуске; передавайте его только сервер-сервер и не включайте в логи или исходный код.

## Порядок первого обмена

1. Проверить ключ через `GET /health`.
2. Передать контрагентов через `POST /counterparties/sync`.
3. Передать договоры через `POST /contracts/sync`. Их `counterparty_id_1c` должен уже разрешаться по `Id_1c` и `counterparty_type`.
4. Передать виды номенклатуры через `POST /nomenclature-types/sync` и единицы измерения через `POST /units-of-measure/sync`.
5. Передать позиции через `POST /nomenclature/sync`, ссылаясь на ранее переданные `unit_id_1c` и, при наличии, `nomenclature_type_id_1c`.
6. Передать валюты через `POST /currencies/sync`, затем курсы через `POST /exchange-rates/sync`, ссылаясь на синхронизированные коды валют.
7. Для чтения справочников, источником которых является приложение, использовать `GET /bases` и `GET /prices`; sync-методов для них нет.

Пакет каждой операции содержит `items` от 1 до 500 элементов. Обмен идемпотентен по `id_1c` внутри конкретного типа сущности. Повторный `id_1c` в одном пакете считается ошибкой элемента. Если обязательная связь ещё не синхронизирована, элемент возвращается с ошибкой и не создаётся; после передачи зависимости его можно повторить.

## Эндпоинты и полезные поля

| Чтение из приложения | Приём изменений из 1С |
| --- | --- |
| `GET /counterparties` | `POST /counterparties/sync` |
| `GET /contracts` | `POST /contracts/sync` |
| `GET /nomenclature-types` | `POST /nomenclature-types/sync` |
| `GET /units-of-measure` | `POST /units-of-measure/sync` |
| `GET /nomenclature` | `POST /nomenclature/sync` |
| `GET /currencies` | `POST /currencies/sync` |
| `GET /exchange-rates?limit=100&offset=0` | `POST /exchange-rates/sync` |
| `GET /bases` | — |
| `GET /prices?limit=100&offset=0` | — |

Поля договоров:

- `id_1c`: UUID договора в 1С;
- `counterparty_type`: `supplier`, `customer` или `carrier`;
- `counterparty_id_1c`: UUID владельца договора в соответствующем справочнике контрагентов;
- `parent_contract_id_1c`: UUID основного договора для приложения, иначе `null` или не передаётся;
- `contract_name`, `contract_number`, `contract_date` (`YYYY-MM-DD`), `status`.

Для номенклатуры передаются `id_1c`, `product_type` (`kerosene`, `pvkj`, `service`), `name`, `unit_id_1c`, необязательный `nomenclature_type_id_1c` и `status`. Позиция требует уже синхронизированную единицу измерения. Поле `is_default` не входит в API: это настройка приложения, и обмен с 1С её не изменяет. Виды номенклатуры требуют `code` и `name`. Единицы измерения требуют `short_name` и `full_name`; для коэффициента пересчёта можно передать `conversion_factor` и `reference_unit_id_1c`.

Для валют передаются `id_1c`, `code`, `name` и `status`. При первой передаче поиск существующей валюты выполняется по точному коду; при совпадении к ней привязывается `id_1c`. Последующие обновления выполняются по `id_1c`; название обновляется из 1С, а локальный `symbol` сохраняется.

Для курсов передаются `id_1c`, `currency_code`, `target_currency_code`, положительный `rate`, дата `rate_date` в формате `YYYY-MM-DD` и `status`. Первичное сопоставление существующей записи выполняется по валютной паре и дате; дальнейшие обмены — по `id_1c`. При обновлении обновляются курс и дата, `source` устанавливается в `1С`. Обе валюты должны быть переданы заранее. Выгрузка курсов использует `limit` (1–500, по умолчанию 100) и `offset` (по умолчанию 0), возвращает `total_count` и `has_more`.

GET-выгрузки справочников возвращают все не удалённые записи, включая ещё не сопоставленные с 1С; у таких записей `id_1c` равен `null`. Это позволяет видеть и сопоставлять ранее созданные в приложении данные до первого обмена. Базисы и цены являются данными приложения и доступны 1С только для чтения. `GET /bases` возвращает не удалённые базисы с их внутренним UUID `id`; `GET /prices` возвращает не удалённые цены страницами до 500 строк. Обе выгрузки требуют интеграционный ключ.

Передаваемые в sync-запросах идентификаторы `id_1c` и внешние ссылки должны быть UUID. В GET-ответах `id_1c` у ещё не сопоставленных локальных записей может быть `null`. Поддерживаются статусы `active`, `enabled`, `активен`, `действующий`, а также `deleted`, `delete`, `deletion_marked`, `пометка удаления`, `удален`, `удалён`. Неизвестный статус отклоняется для соответствующего элемента. Пустой или отсутствующий статус не меняет текущий статус. Удаление выполняется мягко; записи и операционная история физически не удаляются.

Пример создания договора:

```http
POST /api/integrations/1c/v1/contracts/sync
Authorization: Bearer <key>
Content-Type: application/json
```

```json
{
  "items": [{
    "id_1c": "5a96cf72-2bcf-4d5a-bdd8-1afc0d7a7712",
    "contract_name": "Договор поставки",
    "contract_number": "ДП-104",
    "contract_date": "2026-11-05",
    "counterparty_type": "supplier",
    "counterparty_id_1c": "b10a8b22-31f7-4c18-b6e3-552ae6d7f821",
    "status": "active"
  }]
}
```

Ответ содержит `request_id`, агрегированные `counts` и результат по каждому элементу: `created`, `updated`, `deleted`, `skipped` или `error`. Конкретные коды ошибок и примеры схем доступны в Swagger UI.

## Связи и права

- Связь договора с контрагентом разрешается по паре «тип + Id_1c» и сохраняется одновременно как внешний `counterparty_id_1c` и существующий внутренний FK (`supplier_id`, `buyer_id` или `carrier_id`). Несовместимые приложения отклоняются.
- Несвязанные с 1С записи остаются обычными локальными справочными данными.
- Пользователи с правами справочников могут создавать, менять и удалять несвязанные записи. Связанные с 1С записи могут менять и удалять только администратор и генеральный директор; проверка выполняется на сервере, независимо от видимости кнопок. После настройки интеграции создавать и удалять валюты и курсы могут только администраторы. Обычный пользователь может менять у связанной валюты только символ; связанный курс может менять только администратор.
- Внешние ID и статусы нельзя задавать через обычные CRUD-маршруты приложения.
- Каждый вызов записывается в журнал запросов; изменения каждого элемента — отдельно в журнал изменений. Заголовок `Authorization` и секрет API-ключа не сохраняются.
- Новые записи всех импортируемых справочников входят в общую очередь проверки. Подтверждение закрывает проверку, отклонение выполняет мягкое удаление; история изменений общая для всех сущностей.

## Миграция

Миграция `0111_1c_catalog_integration.sql` переводит существующие `id_1c` в четырёх таблицах в UUID, добавляет статусы и внешнюю связь договора с контрагентом 1С. До преобразования она проверяет формат UUID и дубли и завершает работу с явной ошибкой, не обнуляя и не удаляя исходные значения. Миграция `0113_1c_currency_integration.sql` добавляет валютам и курсам UUID-связь `id_1c` и статус интеграции.
