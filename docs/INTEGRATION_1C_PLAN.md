# План интеграции с 1С

## Решения для первого этапа

- 1С является источником мастер-данных по ИНН, названию и полному названию поставщика, покупателя и перевозчика.
- Обмен использует отдельный API-префикс `/api/integrations/1c/v1`; ключи приложения и пользовательские сессии не переиспользуются.
- Ключ показывается администратору только в момент создания/перевыпуска. В базе хранится SHA-256 хеш; перевыпуск отзывает предыдущий ключ.
- Внешняя запись идентифицируется UUID `id_1c`. При первом обмене выполняется поиск по точному ИНН в рамках типа контрагента. Неоднозначный ИНН и конфликт с уже связанным `id_1c` требуют ручного исправления и не приводят к автоматическому связыванию.
- Пакет содержит до 500 записей; частичные ошибки возвращаются по элементам, успешные элементы фиксируются независимо.
- При первом создании запись остаётся видимой, помечается как требующая проверки и подсвечивается до решения администратора. Отклонение выполняет мягкое удаление.
- Удаление в 1С трактуется как мягкое удаление в приложении. Физически строки и связанные складские, ценовые и операционные данные не удаляются.
- Поддерживаемые значения `status`: пустое/не передано (без смены статуса), `active`/`enabled`/`активен`/`действующий`, `deleted`/`delete`/`deletion_marked`/`пометка удаления`/`удален`/`удалён`. Любое другое непустое значение отклоняется для этой строки.
- После создания API-ключа обычные пользователи не могут создавать или удалять контрагентов. Окно редактирования остаётся доступным, блокируются только ИНН и названия записи, связанной с 1С. Администраторы могут создавать, удалять и менять любые поля вручную. Отзыв ключа снимает ограничение на создание и удаление.
- В журнале каждого запроса сохраняются время, метод/путь без query string, HTTP-статус, длительность, количество элементов, IP и User-Agent клиента, размер и тип запроса/ответа, код/описание ошибки, идентификатор ключа и безопасная сводка ответа. Тело запроса и секрет ключа не сохраняются.

## Этап 1 — контрагенты и ключ

1. Добавить поля `id_1c`, `integration_status`, `integration_pending_review`; для перевозчика также `full_name`.
2. Создать страницы администрирования ключа, режима мастер-данных, списка новых записей, подтверждения/отклонения и журнала вызовов.
3. Добавить аутентифицированный тестовый GET `/health`, выгрузку `GET /counterparties` и пакетную загрузку `POST /counterparties/sync`.
4. Разрешить импорт только трёх типов и шести внешних полей (`type`, `id_1c`, `inn`, `name`, `full_name`, `status`). Из входного пакета нельзя менять внутренние поля, связи, цены, права или операции.
5. Записывать отдельные журналы вызовов и изменений с 1С. Не сохранять заголовок Authorization, полный URL с query string или секреты.
6. Проверить миграцию, авторизацию без/с неверным ключом, одноразовый показ и ротацию ключа, сопоставление по ИНН/Id_1c, конфликт и дубли, аудит, мягкое удаление, подтверждение, ограничения ручного API, пагинацию журналов и неизменность связей приложения.
7. Для ручной проверки в development-среде доступны синтетические UI-демо-данные: `npm run demo:1c`; они не используют и не меняют API-ключ и не выдаются за реальный запрос 1С. После проверки удалить их командой `npm run demo:1c:cleanup`.

## Этап 2 — договоры и номенклатура

1. Перевести существующие `id_1c` в справочниках договоров, видов номенклатуры, единиц измерения и номенклатуры в UUID с предварительной проверкой формата и дублей.
2. Добавить UUID-связь договора с контрагентом 1С и разрешать её только по паре типа контрагента и его `id_1c`; сохранять соответствующий внутренний FK в существующей модели договора.
3. Добавить аутентифицированные read/sync методы для договоров, видов номенклатуры, единиц измерения и номенклатуры с пакетами до 500 элементов, идемпотентностью, мягким удалением и отдельным аудитом.
4. Синхронизировать зависимости до зависимых сущностей: сначала контрагенты и договоры, затем виды/единицы измерения, затем позиции номенклатуры. Неразрешённые ссылки отклонять поэлементно, чтобы 1С могла повторить запрос после синхронизации зависимости.
5. Разрешить обычным пользователям CRUD только несвязанных с 1С записей; связанные записи защищать на сервере и визуально помечать в справочниках.
6. Опубликовать Swagger UI и OpenAPI JSON с примерами, авторизацией и ограничениями полей; добавить ссылки на документацию в админ-панель.
7. Проверить миграцию на старых значениях, типы UUID, сопоставление FK, порядок обмена, ошибки ссылок, мягкое удаление, права пользователей, аудит и документацию.

## Этап 3 — сделки: только после согласования контракта

1. Согласовать владельца сделки, состав полей, идентификатор 1С, валюты/единицы, статусы, даты, правила обновления и отмены.
2. Подготовить отдельные read/write схемы для сделок, сопоставление связанных справочников и проверку идемпотентности.
3. Начать с чтения сделок из приложения; запись/обновление включать отдельным ограниченным endpoint после сверки с тестовым контуром.
4. Не отдавать или менять не согласованные внутренние поля и расчётные значения.

## Этап 4 — следующие справочники и транзакционные сущности

1. Добавлять по одной сущности за итерацию с владельцем данных и матрицей разрешённых полей.
2. Для каждой сущности определить обязательные ссылки, обработку удалений, идемпотентность и аудит.
3. Использовать версию API и обратную совместимость; несовместимые контракты выпускать в новой версии.

## Этап 5 — эксплуатация и запуск

1. Проверить TLS на опубликованном endpoint, ротацию/отзыв ключа, резервирование журналов, ограничения частоты и максимальный размер пакета.
2. Сначала подключить тестовую базу 1С и сверить отчёт по созданным, обновлённым, конфликтным и отклонённым строкам.
3. Провести ограниченный пилот; только после подтверждения бизнес-пользователями включать остальные типы данных.
4. Задать срок хранения и процедуру очистки журналов, назначить ответственных с обеих сторон и документировать восстановление после частичного обмена.

## Контракт первого тестового обмена

```json
{
  "items": [
    {
      "type": "supplier",
      "id_1c": "b10a8b22-31f7-4c18-b6e3-552ae6d7f821",
      "inn": "7701234567",
      "name": "Краткое название",
      "full_name": "Полное юридическое название",
      "status": "active"
    }
  ]
}
```

Запрос: `POST /api/integrations/1c/v1/counterparties/sync` с `Authorization: Bearer <key>` и `Content-Type: application/json`. Ответ содержит идентификатор запроса и результат по каждому элементу. Для проверки соединения используется `GET /api/integrations/1c/v1/health`, для тестовой выгрузки локального справочника — `GET /api/integrations/1c/v1/counterparties`.
